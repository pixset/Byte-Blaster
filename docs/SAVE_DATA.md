# 💾 Сохранения и данные

Где что хранится, как устроены слоты и что произойдёт при повреждении файла.

---

## 1. Два уровня хранения

| Слой | Где | Платформы |
|---|---|---|
| Рабочий | `localStorage` | все |
| Постоянный | JSON-файл в `userData` | только Electron |

В браузере и на Android есть только `localStorage`. В десктопной сборке поверх
него работает зеркалирование в файл:

1. **При старте** файл читается через IPC `save:readSync` и раскладывается по
   ключам `localStorage` — дальше вся игра работает как обычно.
2. **При изменении** любого ключа с префиксом `bb` запись в файл ставится в
   очередь с задержкой 250 мс (`saveAPI.write`). Через 800 мс после запуска файл
   создаётся принудительно, чтобы он существовал ещё до первого изменения.

Механизм — перехват `localStorage.setItem`. Поэтому **любой новый ключ с
префиксом `bb` автоматически попадает в файл**, ничего дописывать не нужно.
Ключ без этого префикса в файл не попадёт.

## 2. Ключи

### Прогресс и записи (входят в слот)

| Ключ | Содержимое |
|---|---|
| `bbAdv3` | приключение, обычный режим: `{max, done[]}` + звёзды, осколки, очки по уровням |
| `bbAdvH` | то же для хардкора |
| `bbAchievements` | id открытых достижений |
| `bbAchStats` | счётчики, стоящие за прогрессивными достижениями |
| `bbRecords` | рекорды `{infinite, adventure}` |
| `bbCsFired` | какие катсцены уже показаны |
| `bbCsWorlds` | для каких миров показана вводная сцена |
| `bbRainbow` | собранные радужные осколки |

### Слоты

| Ключ | Содержимое |
|---|---|
| `bbSlot0`, `bbSlot1`, `bbSlot2` | снимок всех ключей прогресса + `meta.updatedAt` |
| `bbActiveSlot` | индекс активного слота (0–2) |

### Вне слотов (общие для всех сохранений)

| Ключ | Содержимое |
|---|---|
| `bbSettings` | **все** настройки — намеренно не входят в слот (и лишь частично уезжают в облако, см. 5a) |
| `bbPlaytime` | наигранные секунды |
| `bbInfRun` | незаконченный забег бесконечного режима |
| `bb_net_nick` | позывной (он же имя в мультиплеере и в профиле) |
| `bb_net_color` | цвет робота в сети |
| `bb_net_lanhost` | последний введённый адрес LAN-хоста |

### Аварийные копии

`bbAdv3_corrupt`, `bbAdvH_corrupt`, `bbRecords_corrupt` — см. раздел 5.

## 3. Как работают слоты

Слот содержит **только прогресс, достижения и рекорды**. Настройки — никогда:
игрок, начавший новую игру, не должен заново выставлять громкость и язык.

Схема «рабочая копия + снимок»:

- Канонические ключи (`bbAdv3`, `bbAdvH`, `bbAchievements`, `bbAchStats`,
  `bbRecords`, `bbCsFired`, `bbCsWorlds`, `bbRainbow`) — это **живая рабочая
  копия активного слота**. Вся игра читает и пишет именно их и о слотах не знает.
- Любое изменение канонического ключа с задержкой 250 мс копируется в
  `bbSlot<активный>`.
- При переключении слота происходит обратное: блоб слота раскладывается по
  каноническим ключам, после чего вызывается `refreshGameState()` — перезагрузка
  прогресса, достижений, рекордов, катсцен, осколков и обновление карты мира.

Флаг `_muting` глушит снимок, пока идёт запись **из** слота, — иначе загрузка
слота тут же перезаписала бы его самого.

Код слотов выполняется **до** `loadAdv()` / `loadAdvH()` / `loadRecords()`,
поэтому активный слот всегда авторитетен.

**Миграция:** если ни одного слота нет (игрок пришёл со старой версии), текущее
одиночное сохранение переносится в слот 1. Прогресс не теряется.

## 4. Сохранение забега бесконечного режима

Ключ `bbInfRun`, модуль `assets/infsave.js`.

- Сохраняется при выходе в меню посреди забега.
- При входе в бесконечный режим появляется выбор: продолжить или начать заново.
- Если сохранения нет — новый забег начинается сразу, без лишнего вопроса.
- **Не сохраняется** в приключении (`advMode`) и в сетевой игре
  (`window.netActive`) — там понятие «мой личный забег» не имеет смысла.

Оверлей `#bbInfResume` (z-index 2600) держит собственные мобильные медиазапросы
в своём же файле: он подключается **после** `ui-fix.css`, поэтому правила из
общей таблицы до него не дотягиваются.

## 5. Повреждённые сохранения

Испортиться сохранение может двумя разными способами, и проверять надо оба.

**Мусор вместо JSON.** `JSON.parse` бросает исключение. Каждый загрузчик ловит
его и:

1. пишет предупреждение в консоль;
2. **сохраняет сырое значение** в `<ключ>_corrupt`;
3. продолжает с чистым профилем.

**Валидный JSON неправильной формы** — `null`, число, массив или объект без
`done`. Такое значение проходит мимо `catch`, и игра падала уже в меню
(`Cannot read properties of undefined`), то есть на чёрный экран. Прийти оно
может из облачного сохранения, из недописанного файла или из ручной правки.
Теперь `loadAdv()` / `loadAdvH()` прогоняют разобранное значение через
`_normProg()`, достижения — через проверку `Array.isArray`, а карты
(`bbCsFired`, `bbCsWorlds`, `bbRainbow`) — через `_plainMap()`. Поведение то
же: предупреждение, копия в `<ключ>_corrupt`, чистый профиль.

Починенное значение **намеренно не записывается обратно** в хранилище: если
местный файл битый, а в аккаунте лежит целое сохранение, запись пустого
профиля тут же уехала бы в облако при включённом автосохранении. Поэтому
экраны, читающие прогресс напрямую (профиль — `prog()` в `assets/profile.js`),
проверяют форму у себя.

Игрок получает работающую игру вместо чёрного экрана, а сырые данные остаются
для восстановления вручную.

## 5a. Сохранение в аккаунте (облако)

Модуль `assets/cloudsave.js`, таблица `cloud_saves` (одна запись на игру).
В облако уходит всё, что игра хранит под префиксом `bb`, **кроме**:

- служебных отметок (`bbCloudAuto`, `bbCloudSeen`, `bbUpdateCheck`,
  `bbUpdateSkip`, `bbLaunchSent`, адрес LAN-хоста);
- аварийных копий `*_corrupt`;
- **настроек, описывающих устройство** (список `DEVICE_SETTINGS`):
  экран и окно (`resolution`, `customResolution`, `gameScale`, `mobileZoom`,
  `windowMode`, `textScale`), производительность (`graphicsQuality`, `gfx`,
  `particles`, `fpsLimit`, `showFPS`, `vsync`, `adaptiveQuality`) и управление
  (`controls`, все `touch*`).

Почему так: `bbSettings` — один JSON, и раньше он уезжал целиком. Загрузка
сохранения, сделанного на ПК, привозила на телефон разрешение окна, тир
графики и раскладку клавиатуры: пропадали экранные кнопки, прыгало качество,
ломался масштаб. Теперь `collect()` вырезает эти ключи перед отправкой, а
`apply()` накладывает облачные настройки на местные (`mergeSettings`), оставляя
«железные» значения нетронутыми. Предпочтения игрока — язык, громкость,
катсцены, тряска, подсказки — переезжают, как и раньше.

Отдельно: отсутствие `bbSettings` в облаке **не стирает** местные настройки, а
битые настройки из облака игнорируются целиком.

Проверяется это `node test-cloudsave.js` (из папки `Game`, зависимостей нет).

## 6. Где лежит файл сохранения

```
Windows   %APPDATA%\byte-blaster\      (точное имя — из package.json)
macOS     ~/Library/Application Support/byte-blaster/
Linux     ~/.config/byte-blaster/
```

Точный путь всегда можно получить в игре — IPC `save:path`. Рядом лежит
`render-mode.json` (см. [PLATFORMS.md](PLATFORMS.md)).

## 7. Правила при добавлении данных

- **Префикс `bb`** — иначе значение не попадёт в файл на десктопе.
- **Решить, часть ли это слота.** Прогресс — да, настройки и сетевые
  предпочтения — нет. Часть слота → добавить ключ в `CANON` в `game.js`.
- **Читать через `try/catch`** с откатом на значение по умолчанию.
- **Не хранить то, что вычисляется.** Общее число звёзд считается из прогресса,
  отдельный ключ для него только разойдётся с реальностью.
