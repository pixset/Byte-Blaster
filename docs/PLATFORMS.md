# 💻📱🌐 Платформы

Одна кодовая база, три платформы. Здесь — чем именно они отличаются и что при
изменении кода надо держать в голове.

| | Десктоп | Android | Веб |
|---|---|---|---|
| Оболочка | Electron 43 (Chromium 150) | Capacitor (WebView) | браузер |
| Протокол | `file://` | `file://` внутри WebView | `http(s)://` |
| Загрузка локалей | IPC | `fetch` | `fetch` |
| Сохранения | `localStorage` + файл через IPC | `localStorage` | `localStorage` |
| LAN-игра | да (`local-server.js`) | нет | нет |
| Сенсорное управление | по настройке | по умолчанию | автоопределение |
| Steam API | да | — | — |

---

## 1. Десктоп (Electron)

### Главный процесс — `main.js`

Создаёт окно, обслуживает IPC и решает проблемы, до которых страница
дотянуться не может.

**Меню приложения удалено:** `Menu.setApplicationMenu(null)` вызывается **до**
`new BrowserWindow`. Иначе Alt открывает стандартную полосу File / Edit / View /
Window, которая игре не нужна и выглядит как баг.

### Каналы IPC

| Канал | Назначение |
|---|---|
| `boot:ok` | рендерер сообщил, что меню отрисовалось (см. тиры рендеринга) |
| `net:lanInfo` | локальные IP-адреса для подсказки в лобби |
| `save:readSync` / `save:write` / `save:path` | файловое сохранение |
| `locale:list` / `locale:read` | чтение переводов под `file://` |
| `audio:read` | чтение mp3-сэмплов |
| `app:quit` / `app:relaunch` | выход и перезапуск |
| `app:openExternal` | открыть ссылку в браузере — **пропускает только `http`/`https`** |
| `resize-window` / `set-window-mode` | размер окна и режим (окно / полный экран / без рамки) |
| `steam:*` | достижения, облако, имя пользователя, статистика |
| `renderer-log` | лог рендерера в консоль главного процесса |

### Тиры рендеринга — лечение «чёрного экрана .exe»

Это самая коварная из починенных проблем, поэтому механизм описан подробно.

**Что было.** Предыдущая попытка обойти сломанный видеодрайвер передавала
`--use-gl=swiftshader`. Это значение удалили из Chromium несколько лет назад
(SwiftShader теперь выбирается через ANGLE), и на сборке Chromium в Electron 43
флаг попадает в недостижимую ветку `gl_factory_win.cc` → `NOTREACHED hit` →
инициализация GL проваливается полностью. Компоновщик не выдаёт ни одного кадра,
окно остаётся чёрным навсегда, **процесс при этом жив и не падает** — ровно то,
что описывали игроки: ни ошибки, ни вылета, просто чернота.

**Что стало.** Игра не спорит с Chromium, а деградирует постепенно и только
после реального провала:

| Тир | Режим |
|---|---|
| 0 | аппаратное ускорение (выбор Chromium по его собственному списку драйверов) |
| 1 | программный GL через ANGLE (`--use-angle=swiftshader`) |
| 2 | аппаратное ускорение отключено полностью |

Тир хранится в `render-mode.json` в `userData`. Каждый запуск заранее пишет
«этот запуск ещё не нарисовал кадр», а рендерер стирает метку через IPC
`boot:ok`, как только меню на экране. Запуск, который так и не нарисовал кадр,
оставляет метку — и **следующий** запуск автоматически опускается на тир ниже.
На здоровой машине игра навсегда остаётся на тире 0.

Флаги командной строки:
- `--safe-mode` — сразу тир 1, без ожидания сбоя (для ярлыка);
- `--reset-render-mode` — сбросить счётчик.

Файл читается с игнорированием BOM: он задуман редактируемым вручную, а Notepad
и `Set-Content` добавляют BOM, из-за чего `JSON.parse` падал бы и тир молча
сбрасывался.

Дополнительно на всех тирах отключается `CalculateNativeWinOcclusion` —
Windows-специфичная функция с долгой историей побеления и подвисания частично
перекрытых окон Electron.

### Диагностика старта

`index.html` расставляет `window.__chk('after <файл>.js')` после каждого
скрипта. В логе видно, какой файл загрузился последним — единственный способ
понять причину чёрного экрана у игрока без DevTools.

## 2. Android (Capacitor)

Проект — `Game/android/`, веб-часть — `Game/www/`. Сборка:
`build/android-build.ps1` (вызывается из `build.bat`).

**Демо и полная версия ставятся рядом:** у демо свой `applicationId`
(`…byteblaster.demo`) и своё имя ярлыка. Без этого установка демо перезаписывала
бы полную игру.

**Выход из приложения** обрабатывается через `@capacitor/app` — кнопка «назад»
на уровне должна ставить паузу, а не закрывать игру.

**Определение JDK** в скрипте сборки идёт по файлу `release` в каталоге JDK, а
не по переменным окружения — они на машинах слишком по-разному настроены.

### CSS-вьюпорт телефона — не то, что показывает эмулятор

Это источник целого класса багов «на телефоне криво, в эмуляторе нормально».
Телефон 2400×1080 при `devicePixelRatio 2.75` сообщает
`window.innerWidth/innerHeight` = **873×393**, а не 2400×1080. Эмулятор с
`dpr 1` сообщает физические 2400×1080.

Отсюда правило: **никаких нижних порогов на размер вьюпорта**. Карта мира
строила канвас `max(640, innerWidth) × max(480, innerHeight)` — на реальном
телефоне высота 393 не дотягивала до 480, канвас получался выше экрана, и вся
раскладка считалась для несуществующей высоты. В эмуляторе порог не задевался и
всё выглядело правильно.

Для проверки в Electron задавай именно CSS-размер и DPR отдельно:

```js
win.webContents.enableDeviceEmulation({
  screenSize: { width: 873, height: 393 },
  viewSize:   { width: 873, height: 393 },
  deviceScaleFactor: 2.75,
  screenPosition: 'mobile',
});
```

### Масштабирование — главная мобильная тонкость

На мобильных **весь `#stage` рендерится в проектном размере 1280×720** и
вписывается в экран через `transform: scale()` (функция `fit()` в
`settings.js`).

Отсюда правило: **медиазапросы должны увеличивать элементы в проектном
размере**. Увеличение, рассчитанное на реальные пиксели устройства, будет
съедено масштабом, и кнопка останется прежней.

Отсюда же второе правило: **сенсорные оверлеи и меню-оверлеи — прямые дети
`<body>`** с `position: fixed`. Внутри `#stage` их сожмёт тем же
`transform: scale()`, и на телефоне они окажутся в «письме» (letterbox) вместо
всего экрана.

Похожая ловушка была в лобби: `fitLobby()` масштабировал панель под экран и тем
самым отменял любое увеличение шрифтов. Вылечено нижним пределом масштаба
(0.62 на сенсорных, 0.4 на десктопе) плюс прокруткой.

### Сенсорное управление (`touch.js`)

- Стиль движения: стрелки / полный джойстик (вверх = прыжок) / джойстик только
  влево-вправо (тогда появляется отдельная кнопка прыжка).
- Джойстик статичный или плавающий (появляется под пальцем).
- Размер кнопок настраивается, раскладка редактируется перетаскиванием.
- Режим показа: авто / всегда / никогда.

### Как игра понимает, что играют пальцем

Раньше по всему коду стояла проверка:

```js
('ontouchstart' in window) || navigator.maxTouchPoints > 0     // ← так НЕ надо
```

Она отвечает на вопрос «есть ли у устройства сенсорный ввод хоть какой-нибудь»,
а не «играют ли на нём пальцем». У любого ноутбука с сенсорным экраном — а
таких давно большинство — она истинна, и человек с клавиатурой получал поверх
игры экранный джойстик, мобильный зум и подсказки для пальцев.

Правильный вопрос задаёт `(pointer: coarse)` — он про **основной** указатель. На
телефоне это палец, на ноутбуке с тачскрином — тачпад, то есть точный.

Общий ответ живёт в `game.js` и экспортируется наружу:

| Функция | Что отвечает |
|---|---|
| `bbIsTouchDevice()` | про само устройство |
| `bbWantsTouchUI()` | то же, но с учётом настройки «Сенсорное управление» |

Оба учитывают и живое поведение: если с устройства хоть раз нажали настоящую
клавишу (`isTrusted`), клавиатура у него точно есть. Остальные модули
(`settings.js`, `network.js`, `results.js`, `tutorial.js`) зовут их через
короткие обёртки с запасным вариантом на случай, если `game.js` не загрузился.

Сам пад в `touch.js` в автоматическом режиме идёт ещё дальше и смотрит на
**последний способ ввода**: пришло касание — показать, нажали клавишу — убрать.
Планшет с чехлом-клавиатурой и ноутбук-трансформер — одно и то же железо с
разными привычками, и гадать по списку возможностей бессмысленно.

Ручные режимы «всегда» и «никогда» перекрывают всё это без вопросов.

## 3. Веб

`build-html.js` собирает статическую версию в `www/`. Ограничения по сравнению
с десктопом:

- **Нет LAN-игры.** Браузер не даст открыть слушающий сокет, поэтому режим
  «ЛОКАЛЬНО» в вебе идёт через тот же онлайн-сервер, и интерфейс об этом честно
  предупреждает.
- **Локали грузятся `fetch`-ем** через `index.json` — язык, не добавленный в
  манифест, в вебе просто не появится (в Electron появится, потому что тот
  читает каталог напрямую).
- **Нет Steam API** и файловых сохранений — только `localStorage`.

## 3.5. Внешние ссылки и встроенный браузер

Все ссылки идут через одну дверь — `window.BBBrowser.open(url)` из
`assets/webview.js`. Магазин, кабинет, вики и страница «Скачать» открываются
**внутри игры**, поверх меню: раньше любая из них выкидывала игрока в системный
браузер, а на телефоне — в другое приложение.

Что модуль решает сам:

| Ссылка | Куда уходит | Почему |
|---|---|---|
| `https://…` на страницу | окно поверх игры | игрок остаётся в игре |
| `.exe`, `.apk`, `.zip`, `.msi`, … | системе | загрузка внутри iframe не начнётся или уедет неизвестно куда |
| `mailto:` и прочее не-web | системе | это не страница |
| сайт, запретивший встраивание | остаётся пустым, через 6 с появляется подсказка «нажмите В БРАУЗЕРЕ» | заголовок `X-Frame-Options` нам не подчиняется |

Наш сайт на GitHub Pages `X-Frame-Options` не отдаёт — поэтому все страницы
студии встраиваются без оговорок.

Платформенные тонкости:

- **Electron.** Страница грузится с `file://`, но iframe на `https` ей не
  запрещён — проверено запуском настоящей оболочки. Файлы по-прежнему уходят в
  `shell.openExternal` через мост preload.
- **Android.** Пока окно открыто, модуль перехватывает аппаратную «Назад» через
  плагин `App` и **снимает подписку при закрытии**: висящий слушатель отключает
  обработку кнопки по умолчанию, и в остальной игре она перестала бы сворачивать
  приложение.
- **Веб.** Внутри iframe живёт третий origin, поэтому вход в аккаунт там может
  упереться в запрет сторонних данных у строгих браузеров — для этого и оставлена
  кнопка «В БРАУЗЕРЕ».

## 4. Чек-лист при изменении кода

| Что меняешь | Что проверить |
|---|---|
| UI-разметку | масштаб на телефоне и планшете, узкие и низкие экраны |
| Работу с файлами | Electron через IPC, веб — только `localStorage` |
| Ввод | клавиатура, геймпад на экране, второй игрок |
| Новый язык | файл + `index.json` + `FLAGS` |
| Флаги Chromium | не выдумывать: проверить, что флаг не удалён из современного Chromium |
| Оверлей | родитель `<body>`, а не `#stage`; `z-index` по таблице из ARCHITECTURE.md |
| Сеть | два окна с разными `partition:` сессии |
| Новую внешнюю ссылку | звать `BBBrowser.open`, а не `window.open`; файл проверить отдельно |
