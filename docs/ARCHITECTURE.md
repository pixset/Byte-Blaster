## 1. На чём всё работает

Никаких фреймворков, сборщиков и транспиляции. Игра — это `index.html`, набор
классических `<script>` без модулей и один `<canvas>`. Причина простая: один и
тот же набор файлов должен запускаться в Electron (через `file://`), внутри
Capacitor-WebView на Android и с обычного веб-сервера. Всё, что требует шага
сборки, ломает хотя бы один из этих трёх маршрутов.

| Слой | Технология |
|---|---|
| Игровой рендер | Canvas 2D (один `<canvas id="game">`) |
| Интерфейс (меню, настройки, лобби, профиль) | DOM + CSS поверх канваса |
| Карта мира | отдельный canvas + DOM-оверлей |
| Логика | ES2020-совместимый JS без модулей |
| Звук | Web Audio API: mp3-сэмплы + процедурный синтез как фолбэк |
| Десктоп | Electron 43 (Chromium 150) |
| Android | Capacitor (WebView) |
| Веб | статические файлы |
| Мультиплеер | WebSocket relay (Node.js на Railway) |

**Последствие выбора «классические скрипты»:** объявления `let`/`const` на
верхнем уровне файла попадают в общую лексическую область, но **не становятся
свойствами `window`**. Поэтому `score`, `gState`, `level`, `lives`, `CT`,
`tick`, `player`, `advMode`, `hardMode` читаются по голому имени, и обращаться к
ним из другого файла надо аккуратно (`typeof x !== 'undefined'`). Для `tick`
специально заведён аксессор `window.__bbTick()` — модулям нужен счётчик кадров,
а имя `tick` слишком легко перекрыть локальной функцией (именно так и случилось
в `status.js`: собственная `tick(p)` затенила счётчик, и `Math.sin(функция)`
дал `NaN` в каждом кадре).

## 2. Порядок загрузки

Порядок в `index.html` — не случайный, он задаёт зависимости.

```
version.js        версия для меню (window.BB_VERSION)
edition.js        редакция сборки: full | demo
webview.js        встроенный браузер (до всех, кто открывает ссылки)
demo.js           ограничения демо (в full — пустышки)
status.js         статус-эффекты от врагов
infsave.js        сохранение забега бесконечного режима
audiofiles.js     загрузка mp3-сэмплов
game.js           ЯДРО: игровой цикл, рендер, уровни, враги, боссы, звук
i18n-new.js       переводы (t(), setLanguage())
settings.js       настройки, масштабирование, тиры графики
worldmap.js       карта мира
achievements.js   достижения
saveslots.js      слоты сохранений
bugfixes.js       поздние точечные патчи поверх game.js
cinematics.js     катсцены
logarchive.js     каталог сюжетных сцен (данные)
profile.js        экран профиля (интерфейс архива логов тоже здесь)
network.js        мультиплеер
touch.js          сенсорное управление
```

Между каждой парой стоит `window.__chk('after …')` — маркер загрузки. Если игра
падает на старте, в логе видно, какой файл был последним успешным: это
единственный способ диагностировать чёрный экран у пользователя, который не
умеет открывать DevTools.

**`network.js` грузится после `game.js` намеренно** — он оборачивает уже
существующие функции ядра (`hurtE`, `updateEnemies`, `drawPlayer`,
`drawBullets`, `startAdv`, `startInf`, `damageBoss`), подменяя их сетевыми
версиями. Обёртки ставятся безусловно через 300 мс после загрузки, поэтому
**ошибка в обёртке ломает и одиночную игру** — так уже было с `hurtE`, которая
принимала три аргумента вместо четырёх и молча теряла флаг «пробивает щит».

**`bugfixes.js` — сознательное исключение** из правила «правь на месте». Там
живут патчи, которые должны применяться после того, как `game.js` полностью
определил свои функции. Файл маленький; если он начнёт расти, это сигнал, что
патчи пора вносить в сам `game.js`.

## 3. Модули и зона ответственности

### Ядро — `assets/game.js` (13 000 строк)

Самый большой файл проекта и его центр: игровой цикл, физика игрока, враги,
боссы, генерация уровней, рендер, частицы, процедурная музыка, HUD, состояния
игры. Разделение по модулям идёт **от него наружу**: новые системы (статус-
эффекты, демо, сохранение забега, профиль) живут в своих файлах и общаются с
ядром через `window.*`-функции.

Ключевые точки входа:

| Функция | Что делает |
|---|---|
| `loop()` | главный цикл: `update()` → `draw()` → `updateHUD()` |
| `draw()` | весь рендер кадра |
| `startAdv()` / `startInf()` | запуск приключения / бесконечного режима |
| `_doRunLevel()` | реальный вход в уровень — последний рубеж всех проверок |
| `hurtE(e, dmg, stomped, pierce)` | урон врагу; `pierce` игнорирует щит |
| `doHurtPlayer()` | урон игроку, i-frames, смерть |
| `doEsc()` | универсальный «назад» — знает, какой экран сейчас активен |
| `worldIdx(n)` | номер уровня → индекс мира (0–10) |
| `advTotalLevels()` | 100 или 110 в зависимости от того, открыт ли секретный мир |

## 4. Состояния игры

Глобальная `gState` — единственный источник правды о том, что сейчас на экране.
Любая новая фича обязана её учитывать, иначе ввод начинает уходить не туда.

```
menu        главное меню
mode        выбор режима
map         карта мира
playing     идёт уровень
paused      пауза
levelclear  уровень пройден
gameover    смерть / кончилось время
```

Поверх этого — DOM-оверлеи со своей иерархией `z-index`. Порядок зафиксирован в
коде, потому что его уже один раз нарушили (профиль на 975 открывался **под**
картой мира на 3000, и экран выглядел неработающей кнопкой):

```
настройки   2000
слоты       2500
итоги       2700
карта мира  3000
профиль     4000
тосты      10000
```

`doEsc()` в `game.js` — точка выхода «назад» для экранов, которые живут внутри
`navScr`. Оверлей со своим модальным поведением (слоты, экран итогов) вешает
собственный обработчик Escape и **обязан** отметиться в `doEsc()`, чтобы одно
нажатие не сработало дважды: `doEsc()` первым делом спрашивает
`Results.isOpen()` и молча выходит. Добавляете такой же оверлей — добавьте туда
же и его проверку.

## 5. Как модули общаются

Три механизма, по убыванию предпочтительности:

1. **Прямой вызов `window.*`-функции.** `status.js` зовёт `window.burst()` и
   `window.floatTxt()` из ядра; ядро зовёт `window.Status.apply()`. Явно и
   отлаживается.
2. **Обёртка существующей функции.** Так работает `network.js`. Мощно, но
   опасно: обёртка обязана пробрасывать **все** аргументы и корректно вести
   себя, когда сеть неактивна.
3. **Чтение глобала по голому имени под `typeof`-проверкой.** Нужно там, где
   значение не является свойством `window` (см. раздел 1). Так `demo.js`
   читает `score` и ставит `gState = 'menu'`.

Чего в проекте **нет** и не надо добавлять: шины событий, DI-контейнера,
менеджера состояний. На 20 тысяч строк это будет слой абстракции без выгоды.

## 7. Правила, которые нарушать нельзя

Эти ограничения выведены из уже случившихся поломок — каждое стоило отладки.

- **Карта мира — координатная.** Никаких сеток кнопок и списков уровней. Один
  мир за раз, орбитальная раскладка, дороги, по которым робот идёт физически.
- **Ни одной пользовательской строки в коде.** Всё через `t('ключ')`. Проверяется
  `tools/find-hardcoded.js`, сейчас 0 нарушений.
- **Сетевые сущности синхронизируются по стабильным ID**, не по индексу в
  массиве — иначе рассинхрон.
- **Сенсорные оверлеи — прямые дети `<body>`** с `position: fixed`. Внутри
  `#stage` их сожмёт `transform: scale()`, которым игра вписывается в экран.
- **Цвет + альфа — только через `withAlpha()`.** Трёхзначный HEX с суффиксом
  прозрачности (`#f0f80`) даёт невалидный цвет: `fillStyle` молча его
  проглатывает, а `addColorStop` падает с исключением.
- **Версия зафиксирована на 1.0.2** и меняется только по явному указанию.
