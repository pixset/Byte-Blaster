## Вкладка «Экран» зависит от устройства

Набор пунктов разный, потому что часть из них физически бессмысленна на
устройстве без окна. Переключением занимается `_syncDisplayRows()` в
`assets/settings.js`, и вызывается она при **каждом** открытии настроек —
игрок может включить сенсорное управление посреди сессии, а панель строится
один раз.

| Пункт | ПК | Телефон / планшет |
|---|---|---|
| **Размер текста** | ✅ | ✅ |
| **Размер интерфейса** | ✅ | ✅ |
| Разрешение окна | ✅ | ❌ скрыт (окна нет) |
| Масштаб игры | ✅ | ❌ скрыт (не участвует в мобильной ветке `fit()`) |
| **Увеличение игры** | ❌ | ✅ |
| Режим окна, V-Sync, FPS, качество | ✅ | ✅ |

### Размер текста (`textScale`)

Увеличение игры делает крупнее **мир**, а эта настройка — **надписи**: HUD,
меню, карту мира, лобби, профиль и саму панель настроек. Нужна прежде всего на
телефоне: вся сцена верстается в «настольном» размере 1280×720 и одним
`transform: scale()` вписывается в экран (см. `fit()`), множитель бывает
0.3–0.5, и восьмипиксельная подпись превращается в три физических пикселя.

- Значения: 80–250 %, шаг 5, по умолчанию 100 %.
- Применяется **сразу при перетаскивании** ползунка, «Отмена» возвращает
  сохранённое значение.
- Устройство своё: в облачное сохранение ключ не уезжает
  (см. [SAVE_DATA.md](SAVE_DATA.md)).

Как устроено: каждое объявление размера шрифта в стилях и в инлайновых стилях
записано как `font-size: calc(Npx * var(--bbText, 1))`, а настройка меняет одну
переменную `--bbText` на `<html>`. Отсюда два правила при добавлении разметки:

1. **Новый размер шрифта пишется в том же виде** — иначе элемент останется
   единственным немасштабируемым на экране (так уже случилось с кнопками
   «ПРОФИЛЬ» и «НАЗАД» на карте мира, где размер выставлялся из JS).
2. **Ширина контейнера не должна зависеть от длины надписи.** Всё, что может
   не поместиться при 250 %, должно переноситься (`overflow-wrap: anywhere`),
   переноситься целиком (`flex-wrap: wrap`) или иметь потолок
   (`font-size: min(calc(...), 8vw)` у заголовка настроек).

Значение читается ещё и маленьким инлайновым скриптом в `<head>` файла
`index.html` — до первой отрисовки, чтобы экран загрузки не дёргался с обычного
шрифта на выбранный.

### Размер интерфейса (`uiScale`)

Текст сам по себе растёт внутри неизменной коробки: отступы, ширины карточек и
кнопок заданы в пикселях под эталон 1280×720, поэтому на 1920×1080 меню
оставалось маленьким островком посреди огромного канваса. Второй множитель —
`--bbUI` — растит сами окна через `zoom`.

Почему `zoom`, а не `transform: scale`: zoom участвует в раскладке, поэтому
содержимое честно занимает больше места, а не растягивается поверх соседей, и
прокрутка внутри окна продолжает работать.

**Правило при правках — про единицы измерения:**

| Единица | Компенсировать? | Почему |
|---|---|---|
| px | нет | им и положено расти — в этом смысл настройки |
| % | нет | считаются от родителя, увеличенного тем же zoom-ом |
| vw / vh | **да, делить на `var(--bbUI, 1)`** | меряются в «неувеличенных» пикселях экрана |

Оба утверждения проверены на живой раскладке: без деления `88vh` окно настроек
вылезало за нижний край, а с делением `100%` оверлей меню накрывал канвас лишь
наполовину.

Деление живёт рядом с самим объявлением размера — в инлайновом стиле панели
настроек и в таблицах, которые `profile.js` и `results.js` подключают во время
работы. Эти таблицы идут в каскаде позже `ui-fix.css`, поэтому положить
компенсацию в общий файл нельзя: она бы просто проиграла.

Не масштабируются намеренно: слоты сохранений и сетевое лобби — они вписываются
в экран собственным скриптом и уже занимают максимум места, а второй множитель
поверх их подгонки сломал бы расчёт.

### Подстройка под экран (`textScaleAuto`, `uiScaleAuto`)

У каждого из двух размеров своя галочка, обе включены по умолчанию. При
включённой галочке ползунок показывает вычисленное значение и не редактируется —
иначе игрок двигал бы его, а размер не менялся. Ручное значение при этом не
теряется: снимите галочку, и оно вернётся.

| Экран | Интерфейс | Текст |
|---|---|---|
| 1280×720 | 1.0 | 1.0 |
| 1920×1080 | 1.25 | 1.25 |
| 2560×1440 | 1.5 | 1.5 |
| телефон 375 px | 1.0 | ~2.4 |

Формулы (`autoUiScale` / `autoTextScale` в `settings.js`): интерфейс растёт
вместе с экраном, но вдвое осторожнее его самого — буквальный ×3 на 4K
превратил бы меню в плакат. Текст на телефоне считается иначе: от того, во
сколько раз `fit()` ужал сцену, потому что именно это и делает его нечитаемым.

Отсюда порядок вычислений: авторазмер текста известен только ПОСЛЕ подгонки
сцены, поэтому каждая подгонка идёт в два прохода — `fitAuto()` подгоняет,
пересчитывает авторазмеры и, если они изменились, подгоняет ещё раз.

Те же формулы повторены в инлайновом скрипте `index.html`: до первой отрисовки
позвать `settings.js` неоткуда, а расхождение было бы видно как рывок размера
сразу после старта. **Меняете формулу — поправьте оба места.**

### Увеличение игры (`mobileZoom`)

Телефон показывает ту же логическую область 800×420, что и большой монитор, —
на 6-дюймовом экране это физически мелко. Настройка увеличивает мир: игрок
видит меньше уровня, но крупнее.

- Значения: `0` = Авто, либо 1.0–2.5 (пресеты 1.0 / 1.25 / 1.5 / 1.75 / 2.0 и
  своё значение).
- **Авто** по ширине экрана в CSS-пикселях: < 520 → 1.45×, < 700 → 1.30×,
  < 900 → 1.18×, иначе 1.0×.
- Реализация — `_viewZoom()` и `_updateViewFocus()` в `assets/game.js`;
  трансформация охватывает фон и мир, но **не** HUD, полосу таймера, шкалу
  босса и виньетку — они рисуются после `restore()`.
- Модификатор `darkness` рисуется **внутри** трансформации: его маска
  строится в мировых координатах.
- На ПК `_viewZoom()` всегда возвращает 1 — путь увеличения не выполняется.

Разрешение рендера при этом подбирается автоматически от фактического размера
канваса на экране (см. [RENDERING.md](RENDERING.md)) — отдельной настройки для
него на мобильных нет и не нужно.

## Преломление радужного мира (`prismFx`, вкладка «Графика»)

Единственная настройка, которая относится к одному уровню игры, — и она нужна.
В 11-м мире (Prism Anomaly) каждый кирпич, шип и враг рисуется через
`ctx.filter` с цепочкой `grayscale → sepia → saturate → hue-rotate → brightness`.
Это самая дорогая операция canvas2d: браузер прогоняет каждый такой объект
отдельным проходом растеризации.

Замер на реальном коде игры (`drawBlocks + drawHazards + drawEnemies`, 23
объекта в кадре): **10.7 мс с преломлением против 1.2 мс без него** при бюджете
кадра 16.7 мс. Квантование оттенка по 20°, которое стояло здесь раньше,
уменьшает стоимость, но не меняет порядок.

| Значение | Что делает |
|---|---|
| `auto` (по умолчанию) | выключено на сенсорных устройствах и на слабых тирах графики (`gfx.glow` или `gfx.bgDetail` < 0.6), включено на остальных |
| `on` | как задумано художественно |
| `off` | без фильтров; кирпичи подкрашиваются дешёвой заливкой |

Что **не** отключается никогда: спектральное небо, призма с веером,
платформы и декор. Они рисуются градиентами и кэшируются (`bgLayer`), их
стоимость и так укладывается в бюджет.

Точка принятия решения одна — `prismFxOn()` в `assets/game.js`; вызывается
один раз на кадр в каждой из трёх функций отрисовки, не на объект.

```javascript
// Меняет внутреннее разрешение canvas
applyGameScale(scale) {
  canvas.width = baseWidth * scale;
  canvas.height = baseHeight * scale;
  // + обновление игровых констант
}

// Меняет размер окна Electron
applyResolution(resolution) {
  electronAPI.resizeWindow(width, height);
  // + вызов fitCanvasToWindow()
}

// Подгоняет canvas под окно через CSS
fitCanvasToWindow() {
  // Вычисляет оптимальный размер с сохранением пропорций
  canvas.style.width = displayWidth + 'px';
  canvas.style.height = displayHeight + 'px';
}
```

**Изменения:**
- ➕ IPC handler `resize-window` для изменения размера окна

**Код:**
```javascript
ipcMain.handle('resize-window', async (event, width, height) => {
  if (mainWindow) {
    mainWindow.setSize(width, height);
    mainWindow.center();
    return { success: true };
  }
  return { success: false };
});
```

# SETTINGS SYSTEM FIX

## Проблема
Система настроек экрана работала неправильно:
- Resolution и Game Scale конфликтовали друг с другом
- Canvas не заполнял окно правильно - оставались черные полосы
- Оба параметра меняли canvas, вместо того чтобы работать независимо

## Решение

### 1. Разделение ответственности

**Resolution (Window Resolution)**
- Меняет размер ОКНА Electron приложения
- Не трогает canvas напрямую
- Доступные значения: 1280x720, 1600x900, 1920x1080, 2560x1440, Custom
- Реализация: IPC вызов в main.js через electronAPI

**Game Scale**
- Меняет внутреннее разрешение CANVAS (canvas.width/height)
- Масштабирует игровой мир (worldW, W, H)
- Доступные значения: 1.0x, 1.2x, 1.5x, 1.8x, 2.0x
- Базовое разрешение: 1024x600

### 2. Система подгонки canvas

**fitCanvasToWindow()**
- Автоматически подгоняет ОТОБРАЖЕНИЕ canvas под размер окна

## Технические детали

### Canvas sizing
- **Internal resolution** (canvas.width/height) - определяет качество рендеринга
- **Display size** (canvas.style.width/height) - определяет размер на экране
- Эти два параметра независимы!

### Aspect ratio preservation
```javascript
const canvasAspect = canvas.width / canvas.height;
const windowAspect = availableWidth / availableHeight;

if (windowAspect > canvasAspect) {
  // Окно шире - подгоняем по высоте
  displayHeight = availableHeight;
  displayWidth = displayHeight * canvasAspect;
} else {
  // Окно выше - подгоняем по ширине
  displayWidth = availableWidth;
  displayHeight = displayWidth / canvasAspect;
}
```

### IPC Security
- Используется contextBridge для безопасного IPC
- Нет прямого доступа к require() из renderer процесса
- Все IPC вызовы идут через preload.js
